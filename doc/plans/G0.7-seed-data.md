# G0.7 — Seed Data (plan)

## Context

G0.7 is the last Phase-0 groundwork task in the [master plan](./00-master-plan.md). It loads the **G0.R research**
([`doc/research/rss-feeds.json`](../research/rss-feeds.json): 10 categories, 115 feeds, fixed popularity) into the
database so the public feed list, ordering, and category filter have real content to render. G0.3 (domain model +
`AddDomainModel` migration) and G0.4 (admin authorization) are done; the entity field names already map **1:1** to
the research JSON, so seeding is a straight projection.

Current state that shapes this:
- `ApplicationDbContext` exposes `Categories`, `Feeds`, `Subscriptions`, `Articles`; `Category.Name` and
  `Feed.FeedUrl` are **unique indexes** (`Data/Configurations/*`). Ids are client-generated GUID v7 via `EntityBase`.
- **Program.cs does not apply migrations at startup** (the template only wires `UseMigrationsEndPoint` in dev).
  G0.7 must ensure the schema exists before seeding.
- No seeding exists yet. `InternalsVisibleTo("LuminaFeed.Tests")` is set, so seeder types can be `internal`.
- Tests use a **SQLite in-memory** connection + `EnsureCreated()` (see `DomainModelTests`).

## Approach

Embed the research JSON as the seed source (single source of truth — no copy that can drift), parse it into DTOs,
and **upsert by natural key** (Category by `Name`, Feed by `FeedUrl`). Insert-missing-only so re-runs are idempotent
and **never overwrite later admin edits** (A1/A2 CRUD). Run at startup after applying migrations.

### 1. Embed the research file (`LuminaFeed/LuminaFeed.csproj`)
Link the doc file as an embedded resource (precedent: the csproj already links `..\.dockerignore`):
```xml
<ItemGroup>
  <EmbeddedResource Include="..\doc\research\rss-feeds.json" Link="Data\Seed\rss-feeds.json" />
</ItemGroup>
```
The loader resolves it by manifest-name **suffix** (`EndsWith("rss-feeds.json")`) to avoid brittle name guessing.

### 2. DTOs — `LuminaFeed/Data/Seed/SeedCatalog.cs`
`internal` records deserialized with `System.Text.Json` (`PropertyNameCaseInsensitive = true`; unknown members like
`generatedOn` ignored):
- `SeedCatalog { IReadOnlyList<SeedCategory> Categories; IReadOnlyList<SeedFeed> Feeds }`
- `SeedCategory { string Name; string? Description }`
- `SeedFeed { string Name; string Category; string FeedUrl; string SiteUrl; string? ImageUrl; string? Description; int Popularity }`

### 3. Loader — `LuminaFeed/Data/Seed/SeedCatalogLoader.cs`
- `static SeedCatalog Parse(Stream)` / `Parse(string)` — pure, unit-testable, guards against null/empty.
- `static SeedCatalog LoadEmbedded()` — reads the embedded resource stream and calls `Parse`.

### 4. Seeder — `LuminaFeed/Data/Seed/DatabaseSeeder.cs`
`internal sealed class DatabaseSeeder(ApplicationDbContext db, ILogger<DatabaseSeeder> logger)`:
- `Task SeedAsync(CancellationToken ct)` → loads embedded catalog, calls the overload.
- `Task SeedAsync(SeedCatalog catalog, CancellationToken ct)`:
  1. Load existing category names → `Dictionary<string,Guid>`. Add each missing `SeedCategory` (new `Category{}` —
     v7 Id auto). `SaveChanges`. Extend the map with the new ids.
  2. Load existing `Feed.FeedUrl`s → `HashSet`. For each `SeedFeed` whose `FeedUrl` is new, resolve `CategoryId`
     from the map (log-and-skip if its category is somehow absent), add `Feed{}`. `SaveChanges`.
  3. Log counts (categories added / feeds added / skipped-existing).
- **Insert-missing-only**: existing rows are left untouched (protects admin edits).

### 5. Startup wiring — `LuminaFeed/Program.cs`
- Register: `builder.Services.AddScoped<DatabaseSeeder>();`
- After `var app = builder.Build();`, in a scope: `await db.Database.MigrateAsync();` then
  `await seeder.SeedAsync(...)`. (Top-level statements already support `await`.) Runs in **all** environments — the
  catalogue is product data. `MigrateAsync` is idempotent and replaces reliance on the dev migrations endpoint for
  schema creation.

## Tests — `LuminaFeed.Tests/SeedDataTests.cs` (xUnit, SQLite in-memory like `DomainModelTests`)
- **Catalog integrity** (C# port of the research `verify.ps1`): embedded catalog loads; `Categories == 10`,
  `Feeds == 115`; every `Feed.Category` matches a category name; `Popularity` values all distinct; `FeedUrl`s
  distinct; required string fields non-empty.
- **Populates DB**: fresh context → after `SeedAsync`, 10 categories + 115 feeds; every `Feed.CategoryId` resolves;
  `Feeds.OrderByDescending(Popularity).First()` is a top-tier feed (BBC).
- **Idempotent**: running `SeedAsync` twice leaves counts unchanged; no duplicate `Name`/`FeedUrl`.
- **Preserves existing edits**: pre-insert a category + a feed sharing a catalog `FeedUrl` but with a changed
  `Name`/`Popularity`; after `SeedAsync` that row is unchanged (insert-missing-only).
- **Adds newcomers**: seed a 1-category/1-feed subset, then the full catalog → missing rows are added.

## Decisions to confirm
1. **Auto-apply migrations at startup (`MigrateAsync`) in all environments** — CHOSEN. ⚠️ **Not production-ready**:
   auto-migrating on startup is unacceptable for a real production system (no review gate, race conditions across
   instances, no rollback). Fine for now / this stage. A code comment and the feature doc must call this out as a
   deliberate temporary shortcut to revisit before any production deployment.
2. **Insert-missing-only (don't update existing feeds on re-seed)** — recommended, to protect admin edits. Alternative:
   also refresh `Popularity`/`ImageUrl`/`Description` from research on every run (treats research as source of truth,
   but clobbers admin changes).
3. **Embed via linked file** (single source of truth) vs. copying the JSON into the project as `Content`. Recommended:
   embed the linked doc file.
